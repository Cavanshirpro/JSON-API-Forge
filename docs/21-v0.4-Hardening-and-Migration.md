# v0.4 hardening and migration guide

v0.4.0 is intentionally different from v0.3.0: it treats security and reliability behavior as part of the public contract. Several configurations that previously loaded permissively now fail fast.

## Migration principle

If v0.3 accepted an ambiguous configuration, v0.4 generally prefers one of these outcomes:

1. make the security choice explicit;
2. reject the configuration at startup;
3. emit a production diagnostic;
4. bound memory/concurrency behavior instead of allowing unbounded growth.

This means some v0.3 applications need configuration edits before v0.4 will start. That is intentional.

---

## 1. Unknown JSON keys are errors

All Forge configuration models use strict Pydantic validation. Unknown keys are rejected.

Old typo:

```json
{
  "rate_limti": {
    "requests": 100
  }
}
```

v0.3 could silently ignore a field depending on the model. v0.4 fails configuration validation.

Why: a misspelled security/performance option should not produce a deployment with unexpected defaults.

Run:

```bash
forge validate
```

before startup and in CI.

---

## 2. Public access is explicit

### Operations

A declarative operation is private unless it has a permission or explicitly sets `public: true`.

Private:

```json
{
  "name": "economy.balance",
  "permission": "economy.balance.read",
  "method": "GET",
  "database": "primary",
  "statements": []
}
```

Public:

```json
{
  "name": "status",
  "public": true,
  "method": "GET",
  "database": "primary",
  "statements": []
}
```

Do not combine `public: true` with a permission; choose one model.

### Custom endpoints

Custom endpoints follow the same rule: permission or explicit public access.

### Data sources

Data-source read access:

```json
{
  "public": true
}
```

only makes reads public. It does **not** make mutation public.

Writable sources require either a write permission:

```json
{
  "writable": true,
  "public": true,
  "write_permission": "catalog.write"
}
```

or an explicit high-risk opt-in:

```json
{
  "writable": true,
  "public": true,
  "public_write": true
}
```

The latter should be rare.

### Event channels

Publishing and subscribing are separate trust decisions:

```json
{
  "name": "notifications",
  "publish_permission": "events.notifications.publish",
  "subscribe_permission": "events.notifications.subscribe"
}
```

or explicitly:

```json
{
  "public_publish": false,
  "public_subscribe": true,
  "publish_permission": "events.notifications.publish"
}
```

## 3. Bootstrap secrets are no longer example passwords

The repository does not ship a usable `change-me` admin key.

Run:

```bash
forge init
```

The bootstrap flow is one-time by default. Recommended lifecycle:

```text
forge init
   ↓
start Forge
   ↓
use bootstrap key once
   ↓
create narrow persistent admin/service key
   ↓
bootstrap principal becomes unavailable
```

A bootstrap key is not a long-term application credential.

`bootstrap_enabled: false` can be used when a deployment has another controlled provisioning method. Do not configure a bootstrap key while bootstrap is disabled.

---

## 4. Production diagnostics are intentionally stricter

Run:

```bash
forge doctor --production
```

The command can report errors for:

- missing/weak bootstrap secret while bootstrap is enabled;
- weak/missing local-HS256 JWT secret;
- Redis-backed features without a Redis URL;
- route collisions or invalid references.

It may warn about:

- wildcard CORS;
- wildcard trusted hosts;
- HTTPS not required by the app layer;
- local media storage;
- SQLite in production;
- process-local rate limiting/realtime.

A warning does not always mean “incorrect.” It means the operator must consciously satisfy the requirement elsewhere.

---

## 5. Idempotency semantics changed

v0.3 stored an idempotency reservation in internal Forge metadata separately from the business database transaction. That left a crash window:

```text
business COMMIT
process crash
idempotency completion not persisted
```

v0.4 idempotent operations maintain the idempotency row in the **same configured business database transaction** as the SQL statements and response record.

The key is bound to a request fingerprint containing the relevant request payload/path/validated parameter inputs. Reusing the same logical key with a different request returns a conflict.

Configuration requirement:

```json
{
  "transaction": true,
  "idempotency": true
}
```

Response caching and idempotency cannot be enabled together for the same operation; idempotent replay is the response-reuse mechanism.

### Scope limitation

This does not produce cross-system exactly-once semantics. If an operation commits PostgreSQL and then calls an external payment API, the external side effect is outside the SQL transaction.

Use outbox/inbox, a durable queue, provider-level idempotency keys, or compensating workflows for cross-system side effects.

---

## 6. Rate limiting changed from concrete-path identity

The primary rate limit is principal-global.

Bad model:

```text
user + GET + /items/1
user + GET + /items/2
user + GET + /items/3
```

Each concrete path could create another bucket.

v0.4 primary model:

```text
project + principal + global
```

Optionally add a second route-template budget:

```json
{
  "rate_limit": {
    "requests": 1000,
    "window_seconds": 60,
    "route_requests": 200,
    "route_window_seconds": 60
  }
}
```

Route identity comes from FastAPI's normalized route template where possible, such as `/items/{item_id}`.

In-memory buckets have:

- idle TTL;
- cleanup interval;
- maximum bucket count.

Use Redis when several processes/hosts must share a quota.

---

## 7. WebSocket messages may be throttled

Connection-time rate limiting is insufficient for a long-lived socket. v0.4 event channels may define:

```json
{
  "websocket_message_requests": 60,
  "websocket_message_window_seconds": 60,
  "websocket_message_burst": 10
}
```

This is separate from connection/global quotas.

---

## 8. Request-body limits are stream-aware

The body-size limit is implemented in pure ASGI middleware that wraps `receive()` and counts chunks. It therefore covers requests without a trustworthy `Content-Length` header.

This does not replace endpoint-specific limits. Media uploads also enforce media configuration limits.

---

## 9. Concurrency saturation behavior now matches configuration

`protection.reject_when_saturated` is behaviorally meaningful.

- `true`: reject excess concurrency quickly;
- `false`: wait up to `max_queue_wait_seconds` for a slot.

Both approaches are bounded. Do not configure a huge queue as a substitute for capacity planning.

---

## 10. Audit behavior is more observable

The audit writer remains an asynchronous bounded queue, but v0.4 exposes queue pressure/drop/write-failure metrics and retries transient write failures.

Important: this audit stream is operational telemetry. It is **not a guaranteed compliance ledger**. If legal/compliance requirements demand durable audit events, use a durable append-only sink/queue/database design and monitor delivery explicitly.

---

## 11. Factory/runtime architecture changed

Project service lifecycle moved to `framework/runtime.py`. Project route creation is separated under `framework/routers/`.

External application configuration should not depend on private Python module layout. If your project imported internal Forge functions directly, treat those imports as unstable in Alpha releases.

---

## 12. New CLI workflow

Prefer:

```bash
forge init
forge validate
forge doctor
forge routes
forge dev
```

The historical `scripts/generate_secret.py` is deprecated. It no longer acts as the documented initialization flow.

---

## 13. JSON Schema files are generated artifacts

Run:

```bash
forge schema
```

CI should verify schemas match current typed configuration models. When changing `framework/config.py`, regenerate and commit schema changes in the same PR.

---

## 14. Suggested migration procedure

1. Create a branch from your v0.3 deployment.
2. Install v0.4 dependencies in an isolated environment.
3. Run `forge schema` and configure your IDE.
4. Run `forge validate` and fix all schema/config errors.
5. Add explicit permissions or `public` flags to operations/data/custom/event definitions.
6. Review any writable public data source; decide whether it really needs `public_write`.
7. Replace copied/default secrets with `forge init`-generated or secret-manager-provided values.
8. Run `forge doctor --production` using production-equivalent environment variables.
9. Test idempotent operations against a disposable database.
10. Test rate limits from every client type (bot, plugin, web, WebSocket).
11. Run the full unit/integration test suite.
12. Deploy to staging.
13. Perform retry/crash/failure tests for critical operations.
14. Back up data and document rollback before production rollout.

Do not upgrade a financial/ledger workflow solely because configuration validation passes; validate domain invariants and transaction behavior with real integration tests.

## 15. JWT is opt-in and local signing can be project-scoped

`security.jwt_enabled` now defaults to `false`. Existing v0.3 deployments that rely on bearer JWTs should make that intent explicit. For local HS256, migrate from one process-wide signing key toward a per-project environment reference:

```json
{
  "security": {
    "jwt_enabled": true,
    "jwt_provider": "local_hs256",
    "jwt_secret": "$env:APP1_JWT_SECRET"
  }
}
```

`JWT_SECRET` remains a compatibility fallback and currently signs local-media temporary URLs. It should not be interpreted as the recommended identity signing key for every project.

## 16. HTTP retry behavior is safer

HTTP data sources no longer retry arbitrary failures indiscriminately. Permanent 4xx responses do not consume retry loops or open the transient-failure circuit. GET/HEAD/OPTIONS/PUT/DELETE may retry configured transient transport/timeout/status failures. POST/PATCH remain one-shot by default.

Only set `retry_non_idempotent:true` when the upstream operation itself has an idempotency contract that makes replay safe. Retrying a charge/order/message without that contract is a correctness bug.

## 17. Realtime listener readiness is explicit

Redis-backed realtime does not report a channel listener ready until `SUBSCRIBE` has been acknowledged. If listener creation fails immediately, that concrete failure is surfaced immediately rather than being hidden behind a readiness timeout. This avoids the first-event race present in less coordinated pub/sub startup designs.

## 18. Cache single-flight state is bounded

Per-key in-process stampede locks are ephemeral and reference-counted. A high-cardinality workload therefore does not leave a permanent Python lock object for every historical cache key. Background stale-refresh exceptions are consumed and logged so they do not become unobserved task failures.

## 19. Media API metadata is intentionally narrower

Normal media responses no longer mirror internal storage records. Physical `storage_key` is internal-only, owner identity is permission-aware, deduplication defaults to owner scope, and a metadata-DB insert failure removes the newly streamed local file. Review any client that previously depended on internal media fields.
