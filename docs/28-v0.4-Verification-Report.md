# v0.4.0 verification report

This document records what was actually verified for the v0.4.0 release candidate and what still requires the canonical GitHub CI environment. Its purpose is to prevent configured checks, skipped integrations, or unexecuted deployment paths from being described as successful runtime evidence.

## Scope

The v0.4.0 hardening work was driven by the v0.3 review and subsequent senior-maintainer self-review. The main targets were unsafe onboarding secrets, idempotency crash semantics, high-cardinality rate-limit state, permissive endpoint defaults, row/tenant authorization boundaries, credential delegation, proxy trust, cache isolation, migration/runtime-DDL behavior, realtime backpressure, media consistency, weak critical-path coverage, application assembly coverage, and release/documentation drift.

The release remains **Alpha**. Passing the checks below is evidence for the tested boundaries, not a blanket production-readiness or exactly-once guarantee.

At this verification point, `docs/` contains **44 Markdown files** and approximately **6034 lines** of documentation, organized from the five-minute starter through security, operations, migrations, failure semantics, known limits, and release verification.

## What the skipped tests mean

The local sandbox does not provide the complete async driver/live-service set used by the integration suite. Tests requiring real PostgreSQL, Redis, MongoDB, or the unavailable local async SQLite driver skip by design in this environment.

Therefore:

```text
18 skipped != 18 live integrations passed
```

The canonical GitHub release workflow must install the full project dependencies and run the PostgreSQL/Redis/Mongo service-container integration job before a `v0.4.0` tag is considered release-validated.

The live CI suite includes, among other checks, PostgreSQL transaction/idempotency paths, one-time bootstrap concurrency, Redis behavior, MongoDB integration, atomic media quota reservation, and `forge migrate` followed by validate-mode startup.

## Security/reliability regressions represented in tests

The v0.4 suite covers, among other paths:

- strict configuration and private-by-default endpoint behavior;
- bounded API-key/bearer input and short-TTL API-key authentication caching;
- one-time bootstrap and credential delegation containment;
- idempotency replay, changed-input conflict, retention, response-size limits, rollback, and same-database atomicity;
- principal-global/normalized-route/pre-auth rate limits and bounded limiter state;
- trusted-proxy CIDR handling, forwarded-header spoofing resistance, project Host/TLS/IP/CORS boundaries;
- ASGI streaming request-body limits and overload behavior;
- cache generation invalidation, owner/principal-aware cache keys, stale refresh, and reclaimed single-flight locks;
- deterministic pagination, protected tenant/owner fields, PATCH/PUT semantics, and database conflict sanitization;
- JSON/YAML/CSV/HTTP data sources, bounded outbound responses, egress guardrails, and retry policy;
- media safe metadata, quota reservation, deduplication, deletion consistency, and partial batch semantics;
- Mongo CRUD/tenant/owner/soft-delete behavior;
- realtime listener readiness, bounded WebSocket queues, per-worker connection ceilings, and message budgets;
- local/JWKS authentication, project-scoped JWT trust, and operator-endpoint separation;
- application factory and runtime partial-startup/cleanup behavior;
- generated router HTTP behavior for SQL/Mongo/RPC/data-source/custom/event/media/admin surfaces.

## Application assembly is part of the release gate

v0.3 had strong individual ideas but weak assembly-level evidence. v0.4 therefore does not exclude the factory/runtime/router layers from quality gates:

- `framework/factory.py`: >=80%
- `framework/runtime.py`: >=80%
- `framework/routers/project.py`: >=75%

This prevents correct lower-level modules from masking a broken middleware, dependency, lifecycle, or generated-route composition.

## Additional local checks

The packaging process also verifies or has locally verified:

- project configuration validation;
- normal and production doctor behavior;
- generated JSON Schema;
- generated OpenAPI operation-ID uniqueness;
- Python source compilation;
- JSON parsing and GitHub workflow YAML parsing;
- TypeScript reference client type-checking with the available system TypeScript compiler;
- Python wheel creation using the locally available build path;
- absence of real `.env` secrets, runtime databases, local media, cache/coverage/build output, egg-info, bytecode, and test caches from the release archive;
- deterministic `MANIFEST.sha256` verification after extraction.

The local npm mirror does not provide the requested TypeScript package, so a local `npm install` is not claimed. A system `tsc` compiler is available and the TypeScript client passes type-checking with it. Canonical CI performs its own Node dependency installation and type-check.

Docker is configured as a required GitHub CI build gate. A local Docker build is **not** claimed when Docker is unavailable in the packaging environment.

## Release rule

A clean source archive can be produced locally, but the canonical GitHub `v0.4.0` release must not be published from a red commit. Push the source tree first, let the Python matrix, live-service integration job, coverage gates, TypeScript job, package checks, and Docker build complete, and only then create/publish the final GitHub tag/release according to `GITHUB_PUBLISHING.md` and `RELEASE_CHECKLIST.md`.
